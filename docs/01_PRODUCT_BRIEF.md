# 01. Product brief / Product charter

| Поле | Значение |
|---|---|
| Название | GuildLife (working title) |
| Категория | Gamified productivity / cozy city-builder |
| Основная ценность | Превратить невидимый прогресс по реальным делам в видимое развитие собственного города |
| Первичный пользователь | Студент / молодой специалист с несколькими параллельными целями и интересом к играм |
| Платформа | Desktop-first responsive web; мобильная адаптация базовая |
| Формат | Открытое портфолио + демонстрационный продукт |
| Владелец решений | Автор проекта; AI-инструменты — ассистенты, не фиктивные члены команды |
| Ограничение | Жёсткий MVP, без монетизации и сложного мультплеера |

## Проблема и JOB TO BE DONE

**Предположение (пока не подтверждено):** обычный список дел показывает «сколько осталось», но слабо визуализирует долгосрочные достижения, поэтому людям трудно сохранять интерес к повседневным задачам.

**JTBD:** «Когда у меня много долгих и разнородных дел, я хочу быстро получить выполнимый план и видеть накопленный прогресс, чтобы не теряться и возвращаться к цели без чувства вины».

## Решение

В одной сессии пользователь формулирует цель, получает предлагаемый AI-план, подтверждает этапы, выполняет первый квест, получает XP/монеты и строит/улучшает здание. Город отражает личные достижения. Один агент-планировщик объясняет предложения и показывает **реальные** статусы, а не псевдоактивность.

## Критерий сильного первого впечатления

За **первые 90 секунд** в демонстрационном сценарии новый пользователь должен понять: (а) зачем он здесь, (б) как создать квест, (в) за что выдаются награды, (г) как награды меняют город. Это **проектная гипотеза/порог проверки**, не подтверждённая метрика.

## Цели проекта (outcomes)

1. Выпустить доступное веб-демо с полным основным циклом и честным README.
2. Подтвердить сквозной сценарий тестами и ручными проверками.
3. Получить реальные наблюдения от 3–5 тестировщиков; до этого не заявлять «validated user demand».
4. Зафиксировать хотя бы 3 осмысленных инженерно-продуктовых компромисса в ADR.
5. Подготовить 2–3-минутное демо и кейс для Technical PM / Project Manager.

## Не-цели

Не строим второй Habitica, не пытаемся создать полноценную стратегию, не интегрируем произвольных внешних AI-агентов, не делаем оплату, PvP, внутриигровой чат, тяжёлую 3D-графику и нативные мобильные приложения.

## Гипотезы с планом проверки

| ID | Гипотеза | Признак | Метод |
|---|---|---|---|
| H1 | Игра делает задачи эмоционально интереснее | Испытуемый добровольно проходит второй квест | 3–5 модерируемых тестов |
| H2 | Создание AI-плана снижает барьер старта | Сможет согласовать план за 2–3 минуты | Тайминг первого сценария |
| H3 | Награды и строительство создают понятную связь | Без подсказки объяснит, за что получил ресурсы | Интервью после демо |
| H4 | Город не отвлекает от реальной задачи | Не вынужден надолго отвлекаться на декор | Наблюдение за сценарием |
| H5 | Рекрутер понимает архитектуру и роль автора | Сможет найти рабочий сценарий, стек и ограничения в README | Проверка README с 1–2 знакомыми |

## Продуктовые принципы

- **Useful first:** задачи реально помогают планировать, декор — усиливает мотивацию.
- **Honest by design:** нет фальшивых агентских процентов, фальшивой автономности, несуществующих метрик.
- **Calm progress:** без потери всего прогресса из-за пропусков.
- **AI is advisory:** модель рекомендует, пользователь подтверждает; бизнес-правила детерминированы.
- **Thin vertical slice:** один полностью рабочий сценарий ценнее восьми декоративных экранов.
