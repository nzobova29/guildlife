# 20. GigaChat и внешние агенты — границы ответственности

**05.11.2026.** Внутренний провайдер **GigaChat выбран пользователем**. Внешние агенты — проектное предложение, код приёма их событий пока не реализован.

## Что GuildLife запускает сейчас

Один планировщик: получает цель и ограничения → обращается к GigaChat → проверяет JSON → сохраняет черновик → ждёт явного принятия. Только после принятия создаёт кампанию и квесты. У него нет доступа к инструментам, начислению наград и произвольному исполнению команд.

В этой версии есть UI проверки/редактирования и серверный адаптер, но реальное обращение к модели требует учётных данных, выбранной модели и положительного дневного лимита. В проверках использованы HTTP doubles, а не настоящий ответ модели. Публичный статус «AI работает» до живого теста не ставим.

## Откуда брать информацию об агентах пользователя

GuildLife выступает **приёмником событий и экраном наблюдения**. Агент выполняется снаружи: у пользователя, в автоматизации или на его сервере. Небольшой адаптер рядом с ним отправляет события на HTTPS endpoint GuildLife. Никаких изменений статуса без события или собственного серверного действия.

Предлагаемый путь:

1. Пользователь подключает источник и получает отдельный ключ с правом `events:write` только для этого источника.
2. Запускает работу в своей системе. Адаптер назначает постоянный `external_run_id` и отправляет `run.started`.
3. Во время работы отправляет `run.heartbeat`, `run.updated` или `run.awaiting_input`.
4. По завершении — `run.completed` с кратким результатом и ссылкой либо `run.failed` с безопасным описанием ошибки.
5. GuildLife сохраняет событие, показывает источник и время получения. Если связь пропала, пишет «нет новых данных», сохраняя последний известный статус. Отсутствие heartbeat не доказывает, что агент завершился или упал.

Это не требует запуска произвольных агентов внутри GuildLife, подключения MCP или LangGraph на первом этапе. Готового SDK пока нет.

## Предложение контракта событий

Endpoint: `POST /api/v1/integrations/{integration_id}/events` — **проект, не работающий маршрут**.

```json
{
  "schema_version": 1,
  "event_id": "uuid",
  "external_run_id": "user-agent-run-42",
  "sequence": 3,
  "type": "run.completed",
  "occurred_at": "2026-11-05T09:00:00Z",
  "title": "Подборка материалов",
  "summary": "Подготовлены ссылки на пять источников",
  "result_url": "https://example.org/result"
}
```

- Владелец выводится из ключа подключения, а не из присланного `user_id`.
- Уникальный `(integration_id, event_id)` делает повтор доставки безопасным; одинаковый id с иным содержимым отклоняется.
- `sequence` помогает не откатывать статус запоздавшим событием. Сохраняем и время источника, и серверное время приёма; проверяем слишком далёкие timestamps.
- Ограничиваем размер тела/текста, скорость запросов и срок хранения. Секреты не принимаем как полезную нагрузку и не пишем в логи.
- Результат показывается как недоверенный текст. Ссылки только разрешённых схем, без автоматического скачивания и исполнения.
- Ключ передаётся в Authorization по HTTPS, хранится хешированным, имеет scope, expiry, возможность ротации и отзыва. Для коннекторов с их собственными webhooks нужна отдельная проверка подписи и replay window.
- Проценты допустимы только если источник прислал измеримое `completed_units / total_units`. Иначе статус и журнал событий.
- `run.completed` **не завершает реальный квест пользователя и не начисляет монеты**.

## Подтверждение и команды

`awaiting_input` означает, что источник сообщил о необходимости решения. На первом этапе GuildLife показывает объяснение и ссылку обратно в систему агента. Кнопки «Продолжить», «Остановить» и «Отправить результат» появятся только с отдельным исходящим протоколом команд, подтверждением получения, авторизацией и аудитом. Сейчас таких команд нет.

## Что решить перед реализацией

1. С каким **одним реальным источником** начнём: пользовательский Python-скрипт, n8n или другая конкретная система.
2. Как источник отправляет события: прямой webhook или локальный адаптер; не обещать подключение любого агента без доработки.
3. Кто владеет подключением. Нынешний гостевой TTL 7 дней подходит для пробного сценария; долговечные подключения требуют аккаунта или другой устойчивой модели владения. Истёкшая гостевая сессия не должна оставлять бесхозный бессрочный ключ.
4. Частота heartbeat, retry с backoff, срок хранения и ограничения публичного endpoint.

**Порядок:** сначала живой GigaChat-планировщик и серверный игровой цикл; затем отдельная небольшая итерация «один источник → реальные события → карточка выполнения». GL-035 остаётся будущей задачей, без фиктивной активности в текущем UI.
